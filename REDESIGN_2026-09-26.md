# Training redesign — 2026-09-26

The owner's report: the neural network stopped improving and is regressing.
This is the diagnosis, the options weighed, what was changed and why, and the
evidence. Numbers are bb per seat-hand from duplicate head-to-heads (the same
deals with seats swapped) unless noted. "Sampled" = both sides play their mixed
strategy; "argmax" = both always take their top action.

## 1. Diagnosis

### 1.1 It was not a regression — it was a stall

- A round robin of nine checkpoints (vSix4 u940 / 1215 / 1240, vSix5 u1245 /
  1248 / 1258 / 1268 / 1278 / 1288; `scripts/h2h_league.py`, shared deals,
  least-squares ratings) is **transitive**: the residuals are no bigger than
  the sampling error, so no rock-paper-scissors cycling.
- The late vSix5 checkpoints sit within +-0.1 of u1248 (u1288 is rated the same
  as u1248). The u1248-1258 "peak" was a lucky high right after the entropy
  drop from 0.16 to 0.10.
- In argmax play every checkpoint from u940 to u1288 is within +-0.1 of every
  other: ~350 updates (billions of rows) changed nothing the network prefers.
  Every sampled-play gain since u940 came from lowering the entropy (making the
  same policy less random).

### 1.2 Why it stalled: each update was mostly noise around a fixed point

- The weights random-walked: after k updates they had moved ~sqrt(k) steps
  from u1248, not ~k; consecutive update directions were anti-correlated
  (cos -0.35).
- Two one-update runs from the same checkpoint that differ only in their random
  seed (`scripts/update_snr.py`) agree on how they change the policy's action
  probabilities at correlation +0.13. About 87% of each update was noise; the
  consistent part was a pull back toward the same point.
- Averaging checkpoints (`scripts/average_checkpoints.py`) did not help, as it
  would if the jitter were around a better centre: the run had converged to
  the fixed point of its recipe.

### 1.3 What set that fixed point

- **The critic was broken.** It grades every move (the actor learns from its
  advantages). From a 2M-row rollout sample with Monte-Carlo returns
  (`PLO5BP_DUMP_BATCH`, `scripts/critic_calibration.py`):
  - it read values 43% too low on average and 2-2.5x too low in its upper
    deciles (+7.9 bb on the river) because its value was a log-space average of
    its predicted distribution;
  - it explained only 29% of the outcome variance (14% on the flop) while seeing
    every player's cards;
  - 77% of its first layer was permanently dead (ReLU units that never fire).
  A brand-new critic trained for ~1 minute on 1.6M rows beat it
  (`scripts/critic_offline.py`: held-out loss 2.60 vs 2.755).
- **The entropy bonus** (0.10) held the policy random; lowering it moves the
  fixed point (large sampled gains; see 3.1).
- **Not capacity:** students distilled from u1290 into far smaller actors
  (`scripts/distill_size.py`) hold its policy — 512x3 (1.1M parameters) and
  1024x3 (3.3M) play the 2048x4 (15M) teacher to within the distillation
  method's own error.
- **Not cycling:** see 1.1.

## 2. Options considered

| Option | Verdict |
|---|---|
| More updates of the same recipe | No — converged; it only adds jitter |
| League / historical opponent pool | Not indicated: no non-transitivity |
| KL "magnet" to a reference policy | Not indicated (no cycling); kept off |
| Weight averaging (EMA/SWA) for serving | Tested: neutral |
| Lower entropy / sizing entropy | Tested: moves the fixed point (3.1) |
| Rebuild the critic | Tested: see 3.2 |
| Give the critic every player's hand strength | Tested offline: tiny gain, not worth the plumbing |
| Smaller actor | Tested by distillation: no loss; faster training |
| Lower learning rate / longer rollouts | Longer rollouts built (half-precision storage); lr kept |
| Suit-isomorphism canonicalization | Deferred (large encoder change, uncertain gain) |

## 3. What changed

### 3.1 Entropy 0.10 -> 0.06, sizing-entropy scale 1.0 -> 0.3

Round 1 (four parallel runs from u1290, 15M rows per update, the same random
stream): after 2-5 updates, vs the u1290 start —

| Entropy | Sampled | Argmax |
|---|---|---|
| 0.10 (control) | ~+0.02 | ~+0.14 |
| 0.06 | ~+0.30 | ~+0.08 |
| 0.03 | ~+0.45 | down to -0.13 |

0.06 takes most of the gain without costing the top action.

### 3.2 The critic, rebuilt

SiLU activations (cannot die), a LayerNorm'd input layer, value read as the
plain mean of its predicted return distribution (unbiased), its action-value
losses scaled by the return variance and the fold value pinned to its exact
value 0 (both were needed: without them a fresh critic's value estimates
collapsed online), extra critic-only passes of many small steps per rollout
(it was getting 16 huge steps per rollout), started from a critic trained
offline on the u1290 rollouts. See CLAUDE.md "Regression diagnosis + redesign"
for the flags.

Online, the rebuilt critic's value loss keeps FALLING (2.55 -> 2.47 within four
updates) while the old critic's RISES as the policy moves (2.70 -> 2.74 over the
same kind of run): the old one could no longer keep up.

### 3.3 Actor size

Round 2 (same recipe, the new critic, 15M rows per update, from u1290): the
distilled 1024x3 student learns at least as well as the 2048x4 network —
after four updates, vs u1290, sampled / argmax: 1024x3 +0.33 / +0.09, 512x3
+0.28 / +0.06, 2048x4 +0.23 / +0.02 (the same no-pool start). 1024x3 it is:
the same results at a fifth of the parameters, faster to act and to train, with
headroom over 512x3 for what later training may need. Final, averaged over
7 checkpoints each: 1024x3 +0.37 / +0.14, 512x3 +0.34 / +0.13, 2048x4 +0.27 /
0.00 (no pool) and +0.32 / +0.01 (with the pool).

Against the LIVE model (vSix5_1248; 61,440 deal pairs each, seed 7), the
round-2 1024x3 model after 8 updates:

| Metric | Result |
|---|---|
| Sampled vs sampled | **+0.39** (z 15) |
| Argmax vs argmax | **+0.09** (z 5; every tier positive) |
| Its top action vs the live model's sampled play | +0.905 (the live model's own top action: +0.979) |
| Its top action vs vSix4_1240's sampled play | +1.32 (the live model's: +1.50) |

The strategy is clearly stronger. Its single most likely action, played
deterministically against a randomizing opponent, is somewhat weaker than the
live model's — the sharper policy mixes differently. The study tab shows the
whole distribution, and grading uses it, so the sampled result is the headline;
the top-action gap is the thing to watch as training continues.

The signal-to-noise re-test (two seeds from the round-2 / round-1 finals) was
dominated by the ongoing sharpening after the entropy cut (both runs moving the
same way), so it could not isolate the critic; the critic is justified by its
accuracy (held-out loss 2.53-2.60 vs 2.71-2.76) and its plasticity (still
improving online while the old one degrades).

### 3.4 Efficiency (all bit-exact unless noted)

- Engine: the actor's hand categories are computed in parallel (a serial loop
  cost up to ~100 ms per step on the river); the hand-strength Monte Carlo's
  board tables are shared by every player acting on a street (-60% of its cost
  at 6 seats); the full observation is written packed (no 4.7 KB dense row per
  table per step).
- Rollout rows stored at half precision in their real-valued columns
  (1,022 vs 1,956 bytes per observation; not bit-exact, relative error 5e-4).

Throughput probe on the final configuration (`scripts/throughput_probe.py`,
40M-row target, the same random stream at every point; rows per second of the
two updates / peak RAM):

| num_envs | Update 0 | Update 1 | Peak RAM |
|---|---|---|---|
| 440k | 127k | 106k | 57 GiB (44M rows) |
| 880k | 140k | 121k | 64 GiB (48M rows) |
| 1.76M | 141k | 130k | 80 GiB (55M rows) |

1.76M envs is the fastest; each stored row costs ~1.2 KB, so the 234 GiB pod
holds ~175M rows: vSix6 runs a 150M-row target (+~14M from the drain) —
2.2x vSix5's 76M rows per update, in about the same wall-clock per update
(~21 min) thanks to the engine work and the smaller actor. (vSix5: ~83k rows/s
overall.)

## 4. The run

`vSix6` (`scripts/vSix6_guardian.sh`), launched 2026-09-26 22:47 UTC on the
RunPod pod: warm from the round-2 1024x3 winner (its Adam state), the 1536x2
critic from its offline init plus one critic-only update, entropy 0.06,
sizing-entropy 0.3, 1.76M envs, 150M-row target, obs rev 1 (drop-in for the
site). Each checkpoint is scored against the live model (sampled, top action vs
sampled, argmax vs argmax) by a watcher on the desktop.

First measured updates: 163-165M rows per update, ~21-22 min each (rollout
~955 s at ~172k rows/s, optimize ~315-355 s), peak RAM 199-202 GiB of 234,
critic value loss 2.47, policy KL per update ~0.002.

vSix6_1300 (its first actor update) vs the live vSix5_1248: sampled +0.34
(z 13), argmax vs argmax +0.08 (z 4.3), top action vs sampled +0.895 (the live
model's own: +0.979). It was promoted to the live site at 23:42 UTC as its
1024x3 actor + the vSix5_1248 critic (the deployed site code cannot rebuild the
new critic, which only feeds the trainer review's "true EV"); backup
`stub.pt.bak-pre-vSix6_1300`.

## 5. Next steps

- Later vSix6 checkpoints: promote (with the owner's OK) when they beat the
  live one clearly; the top-action gap is the metric to watch.
- Deploy the new code so the site can load the new critic.
- A best-response exploitability probe would settle the sampled-vs-top-action
  question properly (not run: ~1 pod-hour per model).
- If the top action keeps lagging, raise the entropy a little for the deep tier
  only (`{"tier_ent": {"deep": 0.08}}` in `runs/vSix6.control.json`).
